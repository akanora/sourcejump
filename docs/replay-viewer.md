# Replay viewer files
What the browser replay viewer downloads besides the replay, and where it comes from.

- Each map's viewer file (`map_viewer_files`, `maps/viewer_file.rs`, packed by `viewer-pack` in the public `sourcejump-packer` repo, a pinned git dependency): the map stripped to what the replay viewer reads (daf's rules: no sounds, no unused model files, no physics, HDR lighting dropped when LDR is there, LZMA undone; map textures capped at 1024 px, `vtf.rs`, lead 2026-10-27), brotli quality 11, stored as `maps/viewer/{map}-{hash}.bsp` with `Content-Encoding: br` and cached for good, so browsers decode it themselves. `GET /v1/maps/{map}` carries it as `viewer_file` (`url`, `bytes`), or null. Staff pack it in their browser and upload it (`docs/staff-api.md`); the CLI's `maps viewer-file` packs one from a file on the server. The viewer fetches it from another origin, so the bucket needs a CORS rule allowing the site (GET and HEAD, any header so range requests pass, exposing `Content-Range`; `scripts/dev-s3.sh` sets it locally).
- CS:S's stock content for the viewer (`maps/stock_content.rs`): the game's own VPK archives (`cstrike_pak`, `hl2_textures`, `hl2_misc`, ≈3.2 GB) stored once under `stock/css-v1/`, uploaded from a CS:S install with the CLI's `maps stock-content <folder>` (skips files already stored). `viewer_file.stock_content_url` says where they are; the viewer reads each archive's `_dir.vpk` index (stored with `Content-Encoding: br`) and then only the byte ranges a map uses, each with its range also in the query (`?range=start-end`) so browsers cache it; storage must ignore that parameter.
